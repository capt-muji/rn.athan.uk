R13 PART 3c: can a London user be served with the network off, forever?

The shipped table: the publisher's 2027 intervals, 365 slots, plus 02-29 from the 2028 year.
  02-29: Fajr 100, Isha 89. Part 3.3 measured this pair identical
  across all 13 leap years in the corpus, so one slot settles it and nothing is interpolated.

== 3c.1 The reconstruction, field by field, over every year available ==
Rules, all from the publisher's own technical page (cited, londonsalahtimes.com/technical):
  sunrise = computed sunrise - 3      Zuhr    = computed transit + 5
  Maghrib = computed sunset  + 3      Fajr    = (that sunrise + 3) - interval
  Asr     = Mithl 1 shadow solve      Isha    = (that Maghrib - 3) + interval
Computed sun: adhan 4.4.6, rounding None, then half-up to the minute.

== 3c.3 Asr, the one field an interval table cannot carry ==

== 3c.4 What the three options actually cost in bytes ==
  Option A, the interval table (366 slots x 2 uint8): 732 raw, 246 brotli
    Needs a computed sun and a computed Asr in the app. Fajr and Isha exact where the sun is exact.
  Option B, all fifty published years (uint16 minutes): 255682 raw, 10290 brotli
    Needs no computation at all. Every value is the authority's own digit. Expires in 2077.
  Option B', ten published years 2027 to 2036: 51142 raw, 6320 brotli
  Option C, one fetched year as the app does today: 53291 raw JSON, 7234 gzip on the wire

  For scale, from R6: the app's 4.9 MB JS bundle and 67 MB release bundle.
  Option B is 0.200% of the JS bundle and 0.0146% of the release bundle.
