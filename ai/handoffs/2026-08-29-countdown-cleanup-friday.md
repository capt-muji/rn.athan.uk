### F.7 — Android minute-boundary skew (status bar vs countdown)

Owner's refined observation (2026-08-29, IMPORTANT — supersedes the ledger's NITZ theory): on the
SAME phone, the status-bar clock flips to the prayer minute while the app countdown still shows
~2–10s remaining. The phone is "ahead" of the app by a variable amount (2s, 7s, 10s).

Critical logical consequence: status bar and Date.now() read the SAME system clock on Android
(SystemClock.currentTimeMillis drives both). Device-clock skew (NITZ) therefore CANNOT produce an
intra-device discrepancy — it would shift both equally. The only things that can make the app lag
its own device clock are: (a) stale displayed values (tick latency — same mechanism as F.6),
(b) deterministic phase misalignment (§3.2 — up to ~1s), (c) the transition hold-latch (§3.3).
F.6 and F.7 are almost certainly ONE root cause with two visible symptoms. Treat them as a single
investigation with two acceptance tests.

## 3. F.6 + F.7 — THE COMPLETE TECHNICAL MODEL (read twice before editing anything)

### 3.1 The five independent tickers

There are FIVE separate 1-second `setInterval` timers running whenever the home screen is mounted,
each started at an arbitrary sub-second phase, each doing non-trivial work per tick:

| # | Where | Created | What it does per tick |
|---|-------|---------|----------------------|
| 1 | stores/countdown.ts:88 `startSequenceCountdown(Standard)` | app init | getNextPrayer + createLondonDate + compare + atom set |
| 2 | stores/countdown.ts:88 `startSequenceCountdown(Extra)` | app init | same, Extra schedule |
| 3 | stores/countdown.ts:171 `startCountdownOverlay` | overlay open | createLondonDate + atom set |
| 4 | hooks/useCountdown.ts:61 (Standard page) | per mount | createLondonDate + getSecondsBetween + setState |
| 5 | hooks/useCountdown.ts:61 (Extra page) | per mount | same, other page |

The home header (components/countdown/Countdown.tsx:22) displays #4/#5's state (or #3's atom when
the overlay is on, Countdown.tsx:33). The STORE tickers (#1/#2) are the authority for transitions;
the HOOK tickers (#4/#5) only drive the header text and can disagree with #1/#2 by up to their
phase offset. components/countdown/Bar.tsx consumes hooks/useCountdownBar.ts, which has NO interval
— it recomputes `progress` at render time from `createLondonDate()` (cheap-ish but another
formatInTimeZone per render; renders happen on every #4/#5 tick).

### 3.2 `createLondonDate()` — the hidden cost AND the hidden truncation

shared/time.ts:15:

```ts
export const createLondonDate = (date?: Date | number | string): Date => {
  const targetDate = date ? new Date(date) : new Date();
  const londonTime = formatInTimeZone(targetDate, 'Europe/London', 'yyyy-MM-dd HH:mm:ssXXX');
  return new Date(londonTime);
};
```

Two facts, each load-bearing:

1. **Cost**: every call runs a full date-fns-tz timezone format (ICU offset lookup, string build)
   plus a Date parse. With 5 tickers at 1Hz plus render-time calls, that's ~7–10 format+parse
   round-trips per second on the JS thread, forever, on low-end Android hardware (the owner's
   OnePlus 8T / Oppo Find X8 — the exact phones reporting F.7). This is self-inflicted tick-jitter
   pressure.

2. **Truncation**: the format string has NO milliseconds (`ss` not `SSS`), so the returned Date is
   floored to the whole second OF LONDON WALL TIME. Every downstream "seconds remaining" therefore
   quantizes to the tick's second boundary, and the displayed digit flips at the *interval's phase*
   (when the setInterval happens to fire), not at the wall-clock `:000` ms boundary the status bar
   flips on. That alone produces a persistent, visible ±0–1s misalignment with the system clock —
   F.7's "not perfectly synced" perception — independent of any load.

Also note what `createLondonDate` is NOT: the returned Date's `.toISOString()` gives the UTC
instant, not the London day (the `XXX` offset survives the parse). The 2026-08-29 test fixes
(7ea441f) learned this the hard way; tests must use
`formatInTimeZone(Date.now(), 'Europe/London', 'yyyy-MM-dd')` for London-day strings.

### 3.3 Rounding and the hold-latch

- `getSecondsBetween` (shared/time.ts) is `Math.floor((to − from) / 1000)`. With `from` floored to
  the tick second (§3.2), the displayed value hits 0 up to ~1s before the true instant, and each
  digit's tenure is ~1s offset by interval phase.
- hooks/useCountdown.ts:65-68 — the **hold-latch**: on each tick, if the freshly computed seconds
  is ≤ 0 it returns `previous` (holds the last digit). This deliberately prevents a frozen "0s"
  while the store ticker's refreshSequence advances the nextPrayer atom. Side effect: any store-side
  transition slowness directly stretches the final visible second — F.6's exact signature.
- Store ticker transition (stores/countdown.ts:93-101): on crossing, it clears its interval, calls
  `refreshSequence(type)` (which cascades: sequence rebuild → nextPrayer atoms → hook effect
  re-runs → new hook interval) and recurses to restart itself. During the clear→restart gap there
  is NO store tick; the hook's latch papers over it by holding.

### 3.6 Fix candidates, ranked (implement AFTER instrumentation confirms which applies)

- **Fix A — kill the per-tick timezone round-trip (do this regardless; it's also F.8-adjacent
  hygiene)**: for a DIFFERENCE `(target − now)`, the London offset cancels — pseudo-space diff equals
  real diff as long as both endpoints share the same DST offset. Compute per tick:
  `secondsLeft = Math.floor((target.getTime() - Date.now()) / 1000)` where `target` is the stored
  prayer datetime (already pseudo-London from createLondonDate at sequence build). DST caveat: if a
  countdown window crosses a London DST transition (last Sunday of March/October, 01:00/02:00 UTC),
  the pseudo-diff is wrong by ±1h — handle by re-deriving the target's offset when
  `getTimezoneOffset`-equivalent changes (date-fns-tz `getTimeZoneOffset`) or simply by detecting
  the rare crossing (at most one prayer per transition-day is affected) and falling back to the
  round-trip path for that window. Add unit tests: same-offset diff, cross-DST diff.
  Effect: removes ~7–10 formatInTimeZone calls/sec AND removes the ms-truncation quantization
  (Date.now() has full ms) — the deterministic ≤1s phase error (§3.2) disappears.
- **Fix B — align tick phase to the wall second**: after Fix A, schedule the interval as
  `setTimeout(tick, 1000 - (Date.now() % 1000))` then `setInterval(tick, 1000)` so digits flip at
  :000 like the status bar. Directly addresses F.7's "seconds don't line up with the phone".
- **Fix C — one shared ticker**: collapse tickers #1/#2 and the two #4/#5 intervals into a single
  1Hz store ticker that writes both schedule atoms; hooks read the atom (no own interval). Halves+
  the per-second work and removes inter-ticker disagreement. Larger diff; consider after A+B prove
  insufficient.
- **Fix D — hold-latch retirement**: once transitions are fast (measured transitionMs small and
  A/B/C landed), the latch at useCountdown.ts:65-68 can show 0s briefly instead of stretching.
  Owner call — the latch was added deliberately (d0598a6 message); do not remove without evidence.
- **NOT a fix**: switching to Reanimated UI-thread clocks or requestAnimationFrame countdowns.
  Owner rejected complexity here repeatedly; the header is a plain Text and stays one.

Acceptance: (1) 10 consecutive mock transitions with inter-tick gaps ≤1100ms in the TICK log;
(2) at a prayer minute, app-displayed 0s occurs within 300ms of the status-bar flip (on-device,
owner-assisted for F.7); (3) 710 existing tests still green + new DST/rounding unit tests pass;
(4) no visual regressions per §3.4's a11y poll (header text still updates every second).
